# 从零设计一个工作流

主册那一节是骨架，这一册补判断标准和常见陷阱。适用于「知道该用 AI，但不知道怎么下笔」的情况。

## 一、先分清三种起点

同样是「想做个工作流」，起点不同，做法完全不同。

| 起点 | 特征 | 从哪下手 |
|---|---|---|
| 有活没流程 | 每次都在重做同一件事，做法还不固定 | 先记录一次真实过程，再抽象 |
| 有流程没工具 | 有 SOP，但全靠人手工跑 | 找出手工最重的三步，优先自动化 |
| 有工具没串联 | 每一步都用了 AI，但它们互不相通 | 先定义交接物，再打通 |

最常见的错误是跳过第一步：还没搞清自己现在怎么做的，就开始设计理想流程。

## 二、记录一次真实过程

设计之前，先跑一次「观察模式」：照平常的做法做完一件事，全程记录。

记四样：

1. 每一步实际做了什么（不是应该做什么）
2. 每步花了多久
3. 每步的产物是什么，存哪
4. 哪一步最烦、最容易出错

第三步最有用。如果某一步的产物是「在脑子里」，那它就是自动化不了的瓶颈，要先想办法把它外化。

## 三、抽象成步骤

把记录整理成步骤，用三条规则筛：

**规则一：按决策点拆。** 这一步的输入、风险、完成标准，和下一步是否真的不同。不同才拆。

**规则二：每步只有一个动作。** 「整理资料并写报告」是两个动作，拆开。

**规则三：每步的产物能独立检查。** 检查不了说明还不够具体。

## 四、给每步定契约

这是全文最值钱的一段。契约包含四行：

```
输入：需要什么，什么格式，没有会怎样
动作：具体做什么，按什么规则
输出：长什么样，含哪些字段
完成：什么条件下可以进下一步
```

「完成」这一行必须能判断是或否。

| 不合格 | 合格 |
|---|---|
| 输出一份分析 | 三列表，最多五行，每行有来源 |
| 检查数据 | 分类合计等于总数，不等就停下来说明差在哪 |
| 写得专业一点 | 不超过 400 字，不用形容词，每条带数字 |

不合格的那一列，模型只能靠猜。合格的那一列，模型能自己判断做没做完。

## 五、串起来，检查三个地方

步骤和契约都有了，串成一列之后检查：

| 检查 | 不合格的信号 |
|---|---|
| 每两步之间有实体交接物吗 | 说不出名词，只能说「上一步的结果」 |
| 有没有某一步可以跳过 | 有，说明它不是必经步骤，降级为可选 |
| 顺序能不能换 | 能换说明没有依赖，可以考虑并行 |

## 六、真跑一遍，找断点

拿一件上周做过的事重做。三种断点，各有对应的修法：

| 断点 | 症状 | 修法 |
|---|---|---|
| 卡在输入 | 某一步发现材料不够 | 把「需要什么」写进上一步的输出契约 |
| 卡在判断 | 某一步反复回来改 | 说明这一步的完成标准不明确，补一条量化条件 |
| 卡在交接 | 下一步用不上上一步的产物 | 交接物的字段设计错了，按下游需求反推 |

## 七、固化

跑通之后三件事，缺一件流程就活不过第二次：

1. **提示词变成模板**，变量标出来
2. **产物存样例**，下次拿它对比
3. **写一句不适用范围**，防止乱套

## 八、六个常见陷阱

| 陷阱 | 表现 | 后果 | 解法 |
|---|---|---|---|
| 一开始就想做大 | 设计一个覆盖全部门的系统 | 三个月没上线 | 先做一条线，跑通再扩 |
| 把教程当流程 | 大段解释背景知识 | 上下文被占满，真正的步骤被淹没 | 只写怎么做，不写是什么 |
| 步骤没有产物 | 某一步「思考一下」 | 无法检查，也无法交接 | 逼自己给每步一个实体产物 |
| 完成标准含糊 | 「质量达标」 | 每次都靠人判断 | 换成可数、可查的条件 |
| 只设计不验证 | 上线才发现跑不通 | 返工 | 必须用真事跑一遍 |
| 不写边界 | 什么场景都往里套 | 简单任务被过度流程化 | 明写「什么时候不该用」 |

## 九、一个最小可用流程的例子

不用七步也能叫工作流。最小可用版本只要三步：

```
输入 → 处理 → 输出
```

比如「客户反馈周汇总」：

| 步 | 契约 |
|---|---|
| 收 | 从三个渠道抓本周反馈，去重，只留带具体诉求的 |
| 分类 | 按功能缺陷、体验问题、需求建议三类归，每条标来源 |
| 出 | 一张表：类别、条数、典型三条原文、建议动作 |

三步，跑二十分钟。它能跑起来，比一个永远在设计的宏大流程有用。

## 十、什么时候该停

设计到一半发现这三个信号，就该收手：

- 这件事一年做两次，建流程不划算
- 流程的维护成本高于手工做的成本
- 每次的输入差异太大，没有稳定的步骤可抽

判断标准还是那条：下个月还做吗。
